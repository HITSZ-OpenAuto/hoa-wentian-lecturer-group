## 如何获取资料

- **只取某一份资料**：在网页上打开对应文件，点“下载”即可，推荐这种方式。
- **整库克隆**：仓库包含约 120 MB 录播视频，完整克隆约 250 MB。网络不佳时建议只下载需要的文件，或使用浅克隆：

  ```bash
  git clone --depth 1 https://gitee.com/jacobbbbb/lecturer-group.git
  ```

- 课件（PPTX / DOCX）可以直接下载后修改成自己的笔记版本，但请保留原作者与出处。

## 协作规范（重要）

多人协作的核心原则只有一条：**先拉取，再改动**。请务必按下面的流程操作。

### 1. 开工前必做：拉取最新代码

在动手改任何文件之前，先执行：

```bash
git pull
```

或在 VS Code 左侧“源代码管理”面板点击“同步更改”按钮（🔄），确保本地是最新版本。

### 2. 本地修改，写清提交信息

完成修改后，提交信息要能让人一眼看懂改了什么，例如：

```bash
git add 离散数学/离散数学（final version）.pdf
git commit -m "新增离散数学第三章复习讲义"
git push
```

### 3. 推送前再确认一次

如果改动期间隔了较长时间，`push` 之前再 `pull` 一次，避免出现 `non-fast-forward` 而被拒。

### 4. 较大的改动请走分支

不要所有人都在 `master` 上直接改。建议：

```bash
git checkout -b 张三-离散数学-期末复习   # 以自己的名字 + 内容命名分支
git push -u origin 张三-离散数学-期末复习
```

推送后在 Gitee 上发起 Pull Request，由负责人审核合并到 `master`。这样即使改坏了，也不会影响主干资料。

### 5. 两条禁令

- **不要 `git push -f`（强制推送）**：会覆盖别人刚提交的内容，几乎无法补救。
- **不要在仓库里提交私人文件**：`.vscode/`、系统缓存、账号令牌、临时导出文件等已写入 [.gitignore](.gitignore)，也不要为了“先存一下”而强行提交。

### 6. 遇到冲突怎么办

`git pull` 后如果提示冲突（`CONFLICT`），说明你和别人改了同一处：

1. 在 VS Code 里打开冲突文件，选择“保留当前更改 / 保留传入更改 / 保留双方更改”；
2. 保存后 `git add` 冲突文件，再 `git commit`；
3. 不确定怎么选时，先在群里问一下，不要直接丢弃别人的修改。

## 分支与提交信息约定

| 分支 | 用途 |
| --- | --- |
| `master` | 主干，保存已审核的资料（建议在 Gitee「管理 → 分支设置」中设为保护分支） |
| `dev` | 日常集成分支，多人协作时先合并到这里，稳定后再并入 `master` |
| `<姓名>-<内容>` / `feature/<内容>` | 个人或单次改动的分支，完成后发 PR |

提交信息建议统一为「动作 + 科目 + 内容」：

- `新增理论力学B期末题型总结`
- `更新机械制图讲义中的尺寸标注示例`
- `修复离散数学讲义第 12 页公式错误`
- `删除重复上传的旧版 PDF`

一次提交只做一件事，不要一个提交里混入多个科目的改动。

## 文件命名与整理

- 一级目录使用课程名（如 `理论力学B`），不要新建“其他”“杂项”这类目录；
- 文件名写清「科目 + 内容 + 版本」，例如 `理论力学期中题型总结.pdf`；避免空格和特殊符号，版本用 `final version` 或日期即可，不要出现 `最终版-最终版-真的最终版`；
- 同一份资料尽量同时提供可编辑源文件（PPTX/DOCX）和导出件（PDF），方便同学阅读、讲师修改；
- 单个文件超过 50 MB（如录播视频）先和负责人确认再提交，避免仓库体积失控。
